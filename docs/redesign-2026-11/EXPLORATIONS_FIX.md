## 1. 顺序调换

原来是：设计系统 → Figma 连接器 → Visual Code Canvas → 插画 Skill。
改成：**Figma 连接器 → 设计系统 → Visual Code Canvas → 插画 Skill**。连接器做好以后，才用它扫描了历史设计稿，所以连接器在前。

## 2. 第 01 节：Figma 连接器（整节替换）

**H2：** 先让 AI 能读写 Figma，后面的整理才接得上

正文：我想让 AI 帮我整理历史设计稿，前提是它能读到、也能改 Figma 文件。所以我做了一个本地 MCP 服务加 Figma 插件：AI 发出任务，插件在当前打开的文件里执行，再把结果传回去。整条链路只在本机运行，不需要 API Key。

`flow`（一行，highlight 第 3 步）：AI 客户端 → 本地 MCP 服务 → Figma 插件在文件里执行 → 结果回传给 AI

正文：让 AI 直接改设计稿，最怕改坏。所以每次任务开始前，插件会先给节点拍快照，出错就自动撤回这次新建的节点；面板上会显示它正在读，还是正在写。

## 3. 第 02 节：设计系统（整节替换，删掉原来的「方法 / 实践」两个小节）

**H2：** 扫描 Qsight 的历史稿后，我发现建好的颜色变量几乎没人在用

正文：我用连接器让 AI 只读扫描了 Qsight 的两批历史稿，一共 19 个页面。文件里已经建了 186 个颜色变量，可页面实际用的是另一个远程库里的变量，第一批页面就用了 39 个。光是蓝色就有三个相近的值，分别用在主操作按钮、品牌标识和改动高亮的文字上。

`MetricRow`（3 项）：19 个 · 扫描的历史页面 ｜ 186 个 · 文件里建好的颜色变量 ｜ 39 个 · 第一批页面实际在用的远程变量

正文：AI 很容易把相近的颜色直接合并。我要求它先不合并：每个颜色按用途单独命名，再由我逐个决定留哪个、怎么合。定下来以后，才把颜色、字体、间距、圆角、描边和栅格写成 Figma 变量，再做成 React 组件库。

`flow`（一行，highlight 第 3 步）：只读扫描 19 个页面 → 列出每个颜色的用途 → 我逐个决定留哪个 → 写入 Figma 变量 → 做成代码组件

正文：目前组件库有 9 个基础组件和 88 个单元测试，用 Storybook 展示每个组件的尺寸、变体和交互状态。

PLATE 02 · 颜色审计：相近的蓝色和各自的用途 ｜ PLATE 03 · Storybook 组件页

小节「从零搭一套设计系统」：
正文：没有历史稿可整理的时候，我用另一个 Skill 从零搭设计系统。它让 AI 在 Figma 里按固定顺序推进，只有一个主 Agent 可以写入，其他角色只读，负责给出规格和验收。

`flow`（一行）：六方向视觉探索 → 浅色和深色色板 → 基础变量 → 基础体系 → 真实组件族 → 组件库验收

状态：Figma 设计系统工作流已开源（GitHub：https://github.com/chenyiwanshishen-source/figma-design-system-workflow）；组件库持续维护中。
